## Conclusion

<!-- crew:conclusion -->
This version fixes what 0.26.1 was meant to fix and did not (plan `usage-fixes`, step n49, added on the user's instruction of 2026-11-20). Two steps of the plan stay open on purpose: rerunning the usage statistics after real use (n37) and the user's judgement of them (n42).

**What happened**

- 0.26.1 (b100658) added three error codes to the list of "the reader is gone" from reading the code, without having seen which code macOS returns. CI on that commit was green on rc/0.21 (run 44654646918) and on the tag (44658230915), and failed on `main` (44658213969, macOS Node 22) in the test "a closed pipe on stdout ends crew without a stack trace and with exit 0". The child printed `Error: write ENOTCONN`, thrown by `lib/core/stream-guard.js`. None of the three codes of 0.26.1 was it. This was found after 0.26.1 was published; 0.26.0 and 0.26.1 stay published as they are.
- The release record of 0.26.1 says the macOS defect was not confirmed fixed. That was right, and the defect was in fact not fixed.

**Verified**

- CI on rc/0.21 at e532924 (run 44671958295): all nine jobs green, including the three macOS jobs, once.
- The injected-error test covers `ENOTCONN`. The worker reported that it fails with "Got unwanted exception: ENOTCONN" when `stream-guard.js` is put back to the 0.26.1 version; the orchestrator did not repeat that control.
- The orchestrator read the whole change.

**Not verified**

- Whether the macOS defect is gone. It shows in roughly one macOS job in eight to ten, so three green macOS jobs are weak evidence; 0.26.1 had six green macOS jobs before it failed. The orchestrator recommended four more rounds of the macOS jobs before this record; the user decided on 2026-11-20 to go on without them.
- Whether `ENOTCONN` is the only code macOS returns. `EPROTOTYPE` and `ECONNRESET` are still guesses and have never been observed. Both closed-pipe tests now print the recorded codes when they fail.
- The plugin has not been tried on a Mac by hand.
- Everything listed as not verified for 0.26.0 still stands: no reviewer, refuter or investigator subagent ran with a real model, the question-widget reply of 0.25, and the two skills in real interactive use.

**Local test run**

- A full local `npm test` on the merged branch: 1219 tests, 1210 passed, 5 skipped, 4 failed. All four are `hooks-sessionjob` tests that start the holder through `wscript`, each timing out after about 32 seconds. The same four fail when that file is run alone on the unchanged 0.26.1 branch, so the change is not the cause. Until 2026-11-19 only one of them failed, and only in full runs; since 2026-11-20 four fail on the development machine also when run alone. The cause was not looked for. The same tests pass in all three Windows CI jobs.

**How the work was reviewed**

- One task, one review round, no findings. The reviewer finished in 13 seconds, so the orchestrator read the change itself as well.
- Every push in this record has its own recorded approval with a user reply; the record shows no `gate.missing` line.

**Known and not fixed**

- The `hooks-sessionjob` holder tests on the development machine (above) and the `hooks-contract` timing test that failed once on a slow Windows runner (run 44549361300). Both are on the to-do list.
