## Conclusion

<!-- crew:conclusion -->
This version carries the first half of the plan `usage-fixes` (steps n8 to n23 and n35), which was written from the usage data of two machines. The second half (n24 to n34, n44) is planned for 0.26.

**Verified**

- CI on rc/0.21 at d697474: all 9 jobs (macOS, Ubuntu, Windows on Node 18, 20, 22) green. The Windows Node 18 job failed on the first attempt and passed on a rerun of the same commit, which the user approved on 2026-11-19. The failed test was `board-autostart`; its own diagnostics show the port it chose (50119) was already in use on the runner. No code was changed between the two attempts.
- Every code task has tests that fail with the change turned off, checked by the worker and, for the three orchestrator fixes below, by the orchestrator.
- Real `claude -p` runs (Claude Code 2.1.316, haiku, a throwaway project with its own data folder, docs/PLUGIN-FACTS.md "Real-run checks for 0.25"): the role card and language line on resume and on a real compaction, and their absence from a fresh start; `--quote` accepted when the words are in the prompt and refused when they are not; a plan-covered merge with no reminder and `approved_by: plan:<slug>`; a merge chained after `crew gate answer` denied before it ran; a push still reminded.
- A full local `npm test` on the merged branch: 1123 tests, 1117 passed, 5 skipped, 1 failed (`hooks-sessionjob` "holder: the session ends…"). A control run of the full suite on 0.24.0 (1c21ba6), with nothing else running, failed the same single test, so the failure predates this version. That test passed in all 9 CI jobs.

**Not verified**

- The question-widget reply. No headless run had the tool or produced its payload, so the payload shape the hook reads is a guess. If it is wrong the widget answer does not count and the user is asked again in text; nothing is approved by mistake.
- The two skills as a whole in real interactive use: that the orchestrator keeps the project language, ends each turn with one status line, keeps going after a merge and asks a whole round in one message. The real runs checked the hooks and the CLI, not this behaviour.
- The board-autostart failure is explained by its log, but no control run shows that the SessionStart change of this version (the role card) cannot have contributed. Two other Windows jobs passed on the same commit.

**How the work was reviewed**

- Three fixes were made by the orchestrator after a task had used both of its send-backs, and were not seen by a reviewer: one line in the approved-hash rule (faa3125), seven lines in the plan cover and the worktree rule (b013f23), each with a test that fails without the fix. Two documentation fixes of one and two lines were read by the orchestrator only. These are the NOT RE-REVIEWED lines below.
- The real-run check task changed documentation only (27 lines in docs/PLUGIN-FACTS.md) and had no review round; the orchestrator read it. This is the NO REVIEW line below.
- One finding marked major stays open on the scope check (a task accepted after its branch was merged, with HEAD ahead of main, can count other tasks' files); it became plan step n44 for 0.26.
- The `gate.missing (merge)` lines below are the local merges of this plan's tasks into rc/0.21. The user decided on 2026-11-18 that an approved plan covers such merges; the code that records this is part of this version, so the installed plugin (0.24.0) still reported them. The push of rc/0.21 was asked and approved (g-1e16da).

**Assumptions that still stand**

- A user message that contains the quoted words is a real approval of that action. The quote is checked against the text of the prompt that started the turn; whether the words were meant as approval is still the orchestrator's reading.
- An unused yes is good for up to 12 hours while it is the latest for its gate and task. The bound was chosen by the worker and accepted by the orchestrator; it is not measured against real use.
- The review rule for fixes after a send-back is followed because the skill says so; nothing in the CLI enforces it yet.
