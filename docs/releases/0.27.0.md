# Release 0.27.0

Range: v0.26.3 (0b31066) .. HEAD (1a1d5bf) (20 commits)

## Conclusion

<!-- crew:conclusion -->
This version cleans up task worktrees after a merge, keeps lessons in the main checkout and tightens two worker rules. It comes from two plans the user approved and that are closed: `skill-pressure-test` (a test of the reviewer and worker prompts under pressure) and `worktree-cleanup` (started when the user found 20 leftover worktrees, 2.3 GB, in another project). The version task itself is outside both plans, on the user's instruction to release 0.27.0.

**What happened**

- Pressure test: 48 real subagent runs, eight scenarios, with and without the crew agent text. The reviewer kept its rules in all 24 runs, and so did the control, so those scenarios do not show whether the text matters. The worker showed two holes: it skipped the full test suite when the brief said a partial run was enough (3 of 3), and it left a hung process tree behind in 2 of 12 runs (`python -` reading a script from standard input). Two worker rules were shown to work: no `git stash` (0 of 12 with the rules, 6 of 6 without) and no disabling of a failing test (0 of 3 with, 3 of 3 without). Report: `docs/research/skill-pressure-test-report.md`.
- The user decided that the rule wins over the brief for the full suite. Both holes were answered with text in the worker files.
- Worktree cleanup: `crew task merge` removes the task's clean worktree after a merge that git confirms in the main checkout; `crew task clean` lists and removes what is left; session start names leftover worktrees and accepted tasks that are already merged; lessons are written to and read from the main checkout everywhere.
- One task (merge removes the worktree) changed a file outside its brief, `templates/crew.json`, because two existing tests require the template to list every default. The scope check stopped the accept, the user was asked and answered that it belongs to the plan.

**Verified**

- CI on rc/0.21 at 1a1d5bf (run 45860882180): all nine jobs green (ubuntu, macos, windows with Node 18, 20, 22).
- Full local suite on the merged branch before the version change: 1265 tests, 4 failed, all four the known `hooks-sessionjob` holder timeouts. The version task's own full run: 1265 tests, 0 failed.
- Worktree cleanup in two throwaway projects with real git, the new CLI against the installed 0.26.2 as control (`docs/research/worktree-cleanup-trial.md`): a clean merged worktree is removed and its branch kept, a changed one stays with the reason, a lesson recorded inside a worktree lands in the main checkout, a merge run from inside the worktree keeps it and prints the command, a cancelled task's worktree stays, `crew task clean` lists and `--apply` removes only the removable one, both session-start lines appear. The control left every worktree and lost the lesson. On this repository's own tasks the new CLI removed four worktrees at `crew task merge`.
- The orchestrator read every diff, and for the two worker-rule tasks ran the new content test with the text and against the unchanged files (it fails there).

**Not verified**

- Whether the two new worker rules change what a real `crewgate:crew-worker` does. The rerun of the scenario could not load the changed agent file in this session, so the old and the new text were given to a general agent as a file to read: all six runs (three old, three new) ran the full suite, so the rerun does not discriminate. It also shows that how the rules reach the agent matters more than their wording. To check: rerun scenario W4 with the real agent type once this version is installed.
- The leftover-process rule was not rerun at all; the hole was occasional (2 of 12).
- The control group of the pressure test was not rule-free: every subagent of the session also read this repository's CLAUDE.md, which overlaps with two of the rules under test. The orchestrator designed and graded the scenarios itself, and two of its mechanical checks were wrong and were overridden by reading the transcripts (W3, W4).
- Adopting an untracked lessons file left in a worktree, a removal that git refuses, and the size limit of `crew task clean`: unit tests only. Squash and rebase merges are not recognised as merged by design. Everything ran on Windows only, apart from CI.
- The session-start hook is about 90 ms slower when accepted tasks with a branch exist (median 608 to 700 ms on this machine, worker's measurement); its timing test has a 1000 ms limit and failed once in a full run under load on a branch that did not touch the hook.
- `docs/DESIGN.md` and `examples/todo-cli/WALKTHROUGH.md` were not checked and may still describe removing worktrees by hand.
- Everything listed as not verified for 0.26.0 to 0.26.3 still stands.

**How the work was reviewed, and how to read the flags below**

- Eight tasks. Every one had a review round; three were sent back or re-reviewed (lessons location: one send-back, two rounds; merge removes the worktree: one send-back, two rounds). The reviewers finished in 13 to 33 seconds each and several said they ran no tests, so the orchestrator read each diff and ran the new test files itself.
- "NO REVIEW: this task has no finalized review round" appears on three tasks (t-20261126-k4iw, t-20261126-l6vh, t-20261126-mptl). Each of them was reviewed; the rounds are not finalized because every finding that survived the filter was dismissed with a written reason instead of going to the refuter, and `crew task accept` treats such a round as decided. The dismissals and their reasons are listed under each task. One of them (k4iw) was accepted with `--skip-refuter` for a single cosmetic finding.
- One finding in this range came from the orchestrator and not from a reviewer: the function that brings lessons back from a worktree reported a failure as "nothing to adopt". It was sent back and fixed before the task that depends on it was written.
- "gate.missing (merge): `git merge`" is from the trial of the worktree cleanup: the `git merge` commands ran inside the two throwaway projects, not in this repository, and the hook counted them for this session. Every merge into rc/0.21 was either covered by an approved plan or, for the version task, by its own recorded approval with a user reply.
- The last `push` line says "NO ANSWER RECORDED". The answer exists: it was recorded as yes with a user reply at 2026-11-26T16:40:03Z, and the push event carries `approved_by: gate:g-15ef5e`. The list stops at the last commit of the range, which is older than the answer; the same happened in the 0.26.3 record. This is a defect of the record and is on the to-do list.

**Known and not fixed**

- A full test run can leave a `board serve` process behind (found once, in a worker's worktree; which test leaves it was not looked for).
- Workers still leave background wait loops running after they report: three workers of this range did, and two said nothing was left. The new rule addresses it but is unverified, as above.
- The `hooks-sessionjob` holder tests on the development machine and the `hooks-contract` timing test, as before.

### worktree-cleanup - worktree 用完就清

- Goal: 任務合併或結束後，Crewgate 自己清掉它的 worktree，或至少清楚告訴使用者還留著哪些、佔多少空間，不再讓空間被默默吃掉。
- Completion: 6/6 (100%)
- Clarified:
  - Q: 合併後自動移除？ A: 是：crew task merge 記錄合併時，分支已在 HEAD 裡且 worktree 沒有改動就移除；分支留著；有改動不移除並說明原因
  - Q: Crewgate 自己寫的檔案算不算改動？ A: 只有 Crewgate 自己產生的檔案（.crew/ 底下）時當成乾淨，但先把裡面的經驗搬回主目錄再移除
  - Q: 取消的任務也自動移除？ A: 不要，只在開場列出
  - Q: 開場提醒？ A: 列出已合併或已取消但 worktree 還在的任務數量和清理指令，不算佔用空間
  - Q: 一次清理的指令？ A: 新增 crew task clean：預設只列出可清的 worktree 和佔用空間，--apply 才移除；有改動或分支沒合併的只列出不動
  - Q: 在 worktree 裡記經驗寫錯位置？ A: crew lesson add 一律寫進主目錄的 .crew/LESSONS.md
  - Q: 已驗收但沒記錄合併？ A: 分支已合併而任務停在已驗收時，開場提醒執行 crew task merge
  - Q: 怎麼判定已合併、在哪裡判定？ A: 以主目錄（專案根目錄）的 HEAD 為準：任務分支的最新 commit 是它的祖先，而且 git 確認合併後才移除。squash 或 rebase 合併判不出來，只列出、不自動移除 **(decision)** - chosen by the model, not confirmed by the user
  - Q: 怎麼算乾淨？ A: git status --porcelain 沒有輸出（含未追蹤檔）。唯一例外是未追蹤的 .crew/LESSONS.md：先把主目錄沒有的經驗附加回主目錄，搬不成就不移除 **(decision)** - chosen by the model, not confirmed by the user
